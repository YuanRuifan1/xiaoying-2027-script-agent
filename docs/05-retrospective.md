# 复盘与下一步

以下是本次实现观察，不替候选人虚构个人学习经历。

最难的边界是“生成脚本”和“证明脚本可用”的区别。来源 ID 存在，并不代表具体产品主张受到支持；模型说检查通过，也不代表调用过工具。解决方式是用事实原文核对主张，并由程序检查当前脚本版本的真实报告。

为保证首版可验证，选择了受控文案。代价是风格自由度低，正确的自然语言改写也可能被拒绝。后续应把事实主张与创作性表达分开，用更丰富的批准表达、语义支持检查及人工标注集衡量误拒绝和漏检，不能只增加提示词就声称解决幻觉。

首次真实调用成功检索后遭遇 HTTP 429，记录保存于 `examples/runs/glm/initial_429_failure/`。这暴露出单步接口可用不等于完整链路稳定。增加有界退避和请求间隔，并记录每次 HTTP 尝试；网络重试没有被计为模型自主调整。

自动化测试覆盖了过期检查、有效 ID 搭配虚假主张、语音过长但画面很短、资料内容变化等边界。这些测试比断言固定生成措辞更能检验系统责任。

还观察到一次模型在调用时长工具之前就主动缩短初稿（保存在 `examples/runs/glm/over_duration_preemptive_edit/`）。最终通过不等于证明“观察工具反馈后修订”。因此新增前置条件：初稿先载入当前状态，模型调用时长工具观察后才允许编辑；修订方案仍由模型选择，并新增对应测试。

下一步优先级：候选人独立复现与审阅；扩充事实/风格数据并增加检索改写评估；引入真实配音时长测量；最后再考虑交互界面和线上部署。

实际耗时见 `examples/worklog.json`。以实际记录区间为准，不预先宣称三小时内完成。GitHub 授权等待与候选人的离线工作时间无法由程序准确推断。
